加 `alsoSatisfiedBy?: string[]`。四个顾虑的答案：

1. **波及面为零**（关键）：节点结构住在 TS 源码里，而 925 处 `flags.event.<id>` 引用、

2. **显示只显主承载**。「以下任一」是把一堵墙推给玩家，与本轮治"方向感"的目标相反。

### P1-10　29% 的 objective 只写方法不写结果

实测（2026-08-17）：415 条有 objective 的 event 里，**119 条（29%）只绑方法**
（`向X追问`／`前往X`／`随X进入`／`找X借`），说结果的（`查明`／`保住`／`扛住`）只有 87 条（21%）。

最典型是 `stage_08` 一串八条里六条以"在某地做某事"开头：「在庭院迎接苏妲己」把
**地点＋对象＋动作**全绑死——玩家不在庭院、或不想迎接，这一拍就没法完成。

**不能直接批量改**，两个硬约束：

1. **`objective` 被两个模式共用**——模块注释明写 canon_companion 侧栏也读 `view.objective`。
   world_sim 要"结果导向"，canon_companion 要"照原著走"，**两边诉求相反**。
   若确认要分叉，该加 `worldObjective` 之类的新字段，而不是把同一字段改来改去。
2. **`playerCompletionContract` 的动作 id 常与 objective 措辞配对**，改一头会让判定与显示脱节。

**建议的最小集**：只改任务链已认领的那批（九条线共认领约 100 条，其中绑方法的三四十条）——
那才是玩家照待办走会被卡住的；其余没上链的改了没人看。

## P3 · 新建，依赖前面的东西

### P1-4　声望没有确定性模型，全凭 LLM 自觉 ⚠ **P3-1 的前置**

用户指出（2026-08-16），已核实：

| 事实 | 证据 |
|---|---|
| 引擎无任何确定性写声望处 | 全仓 `声望` 出现处均为初始化 0（`gameStateStore.ts:393`、`sectSystemFactory.ts:98/159` 等） |
| 声望是 LLM 可写路径 | `commandValidator.ts:34` 列入白名单 |
| 唯一约束是文字指引 | `storyContext.ts` reputationLine：救人除害 +30~300、斩强敌 +100~1000、震动一方 +200~2000 |
| 档位只做展示 | `reputationTier`（籍籍无名 → 传说人物，8 档） |

**给多少全凭模型当场决定。** 这违反项目自己的原则——确定性调度定"发生什么"，LLM 只管"怎么讲"。

**同一仓库里已有正确做法可照抄**：好感有确定性结算——`affinityLadder.ts` ＋
`runtime.ts:2418`「共历事件好感结算」（R3-9 §7），并以 `已结算共历好感的事件` 防重复。
声望应比照：**承重事件完成 → 引擎给确定性增量**，LLM 只负责叙述扬名的过程。

**为什么是 P3-1 的前置**：商队经营层的定义是「别处的地位在此处折现」。
若地位本身由模型随手给出，折现出来的就是模型心情，不是玩家的经营成果。
