# 稳定物品获得机制（2026-08-21）

## 结论

物品获得不能继续以“正文写了拿到 → 模型记得补背包指令”为主路径。稳定路径必须是：

> 世界中先有一个确定物品 → 本地动作得到确定结果 → 本地交易原子落账 → 正文只演出回执。

LLM 可以写“怎么递过来、玩家什么感受”，但不能决定这件物品是否真的进了背包，也不能自行给它改名、改品级或重复发放。

## 当前不稳的原因

现有自由叙事路径依赖两个概率环节：

1. 指令模型从正文识别“获得／接过／拾取／购买”；
2. 系统再用中文句式与物品名启发式检查有没有漏写背包。

措辞、别名、数量、JSON 结构或重试任何一处变化，都可能漏账、错账或重复叠加。`narratedInventory` 适合做旧档修复与异常审计，不适合继续当物品系统的权威来源。

## 统一交易合同

每次物品转移必须有四个稳定身份：

- `transferId`：这一次转移的唯一 ID；刷新、重试、重复处理仍只结算一次。
- `itemId`：指向当前剧本 catalog 中的物品；名称、类型、品级、描述从 catalog 取，不从正文猜。
- `quantity`：本次变动数量。
- `source`：来自哪个事件、哪个本地动作、什么 outcome、哪一世界回合。

本地事务同时写两处：

1. `角色.背包.物品.<itemId>`；
2. 受剧本运行时保护的 `inventoryTransferReceipts`。

只有两处都成功，才算获得。回执是幂等账本，也是以后查“这件东西怎么来的”的来源记录。

## 三类获得方式

### 1. 固定剧情物品

例如王哲交锦囊、NPC 交信物、任务结算给奖励。物品和发放条件已知，直接挂在本地事件动作的 `outcomeEffects.inventoryTransfers`。这是本轮已经实现的稳定通道。

### 2. 世界探索／战利品

搜索、战斗、开箱先由本地判定决定是否成功；成功后从地点／敌人／容器的确定 loot catalog 生成 transfer，再走同一个结算器。正文不得先写玩家已经拿到未知战利品。

### 3. 即兴赠送／商店新货

LLM 只能提出一个“待领取物品”草案，先经过结构校验并登记进当前场景 catalog；本轮最多写 NPC 拿出、报价或递到面前。玩家下一次明确接受／购买，且本地检查价格与条件通过后，才生成 transfer。这样允许即兴内容，又不让模型直接改背包。

## 叙事与 UI

- 正文读取已结算回执，只演出已发生的获得；没有回执就不能写“收入囊中”。
- 状态变化流显示“获得物品【名称】×数量”，不需要玩家再点一个领取按钮。
- 背包详情可显示来源事件与获得回合；这是审计信息，不做开发者式倒计时。
- 旧的正文识别补账保留为兼容兜底，但遇到本地已结算物品时必须跳过，避免二次叠加。

## 本轮纵切

已实现：

- 本地 catalog 物品的原子发放；
- `transferId` 幂等去重；
- 同一 `itemId` 的确定性数量叠加；
- 交易回执跨关继承；
- 模组校验：物品引用、数量、ID 命名空间、重复 transfer；
- 本地已发放时，拒绝 LLM 对同一背包路径再次 set/add；
- 正文补账兜底跳过本地已结算的同一物品。

未在本轮擅自改 canon 数据：清羽开局第一关没有合适的“新获得 catalog 物品”；最自然的首个真机验收点是后续王哲交付锦囊。应在逐拍核准该节点后，把锦囊 transfer 挂到对应成功动作，不为测试凭空发奖励。
