## 1. 问题：世界状态由原著快照决定，而不是玩家轨迹

`stage-projection` 是 registry 给每个角色按关卡投影的身份，**本质是原著轨迹的静态快照**。243/315 名角色有它。

它假定玩家走了原著线。于是：

- 孙寿在 `lyg.changgan_begins` 的 `role` 写死为「程宗扬内宅侍婢」——**哪怕玩家整条云龙线从未见过她**。
- 玩家没救的人，在后续关卡的投影可能仍是"获救后的样子"。

而整个 R2-0 分歧账本就是为"玩家可以不走原著"建的。**两套机制在设计上互相冲突**，且冲突面覆盖 243 个角色的所有投影字段。

### 现有的"相识"推导为什么不够

`collectIntroducedCharacterIds`（`storyContext.ts:214`）从"已激活/已完成事件的 relatedCharacterIds + opening.featuredCharacterIds"推导出一份名单。三个致命限制：

1. **不持久化**——只写进 `createScenarioPromptState` 产出的 `structuredClone` 副本，不落存档。
2. **不跨关**——`runtime` 与两个 initializer 都不带它，切关后从零重推。
3. **不是相遇记录**——它记的是"剧情走到哪"，不是"玩家见过谁"。事件被 void（玩家用别的方式绕过）时语义直接失真。

## 2. 地基：相识账本

一条记录回答"**我在何时、何地、以什么方式、遇到了什么处境的谁**"。

```jsonc
{
  "characterId": "liuchao.character.sun_shou",
  "atStageId": "lyl.taiquan_sacred_fruit",
  "atEventId": "lyl.event.s04_02",
  "atWorldTurn": 37,
  "kind": "encountered",        // 见 §2.1
  "circumstance": "captive",    // 见 §3：相遇时她的处境
  "identityAtMeeting": "襄城君、吕冀之妻",   // 当时她是谁——不是她后来是谁
  "divergenceRefs": ["div.lyl.lvshi_fall"]  // 相遇时的世界状态依据
}
```

### 2.1 相识程度（kind）

不是布尔值。**"听说过"和"见过"是两回事，而传闻找人那套闭环需要前者能记账**：

| kind | 含义 | 典型来源 |
|---|---|---|
| `rumored` | 只听过传闻，未见其人 | 征兆 `observableFacts`、他人转述 |
| `introduced` | 被引荐/远远见过，尚无实质接触 | 同场但未交谈 |
| `encountered` | 亲历接触，可对话可互动 | 事件相关、同场交谈 |
| `joined` | 已归入阵营/后宫（正典加入事件已发生） | `joining` 事件、关系标签变更 |

`joined` 正是 `affinityCaps` 里 cap 的解除条件——两处用同一个事实，不另立标志。

## 3. 相遇处境 = 相识节点 × 世界状态

**这是本文的核心，也是 stage-projection 无法表达的东西。**

孙寿的 registry 本来就写了两副面孔：

> personality：「**上位时**骄横歹毒、贪婪虚荣、心狠手辣」｜「**落难后**卑微自称『犯妇』摇尾乞怜」
> keyEvents：「吕氏倒台沦死囚，交程宗扬＋阮香琳审讯…」

她是谁，取决于玩家什么时候撞见她：

| 相遇时机 | 处境 | 她怎么对你 | 可获得性 |
|---|---|---|---|
| 吕氏当权时 | 襄城君，有权有势 | 骄横、根本不理你 | cap 极低，攀附无门 |
| 吕氏倒台后 | 死囚／刑场／人市待售 | 拼命攀附，卑微乞怜 | 可得，但那是绝境求生不是好感 |

**同一个人，两条完全不同的关系曲线。** 处境由相遇时的世界状态决定，而世界状态的偏离**分歧账本已经在记**——两本账合起来才算得出"你见到的是哪一个孙寿"。

### 处境（circumstance）的取值

建议先给一个小的封闭集，够用即可：`in_power` / `neutral` / `fallen` / `captive` / `fugitive` / `deceased`。由**世界状态推导**，不由 LLM 声明。

## 4. 四个上层消费者

地基一旦有了，前面反复讨论的问题都落在它上面：

| 消费者 | 怎么用 |
|---|---|
| **在场判定**（`presence.ts` 已落地） | 未相识者不得登场；`rumored` 只能出现在传闻里 |
| **好感上限**（`affinityCaps.ts` 已落地） | `joined` 是 cap 解除条件；未相识则 cap 压在陌路 |
| **队伍随行** | 随行是 `joined` 的下游状态，不是独立系统 |
| **离场职责推进** | 只有相识过的人需要推进；`joined` 者才有驻地与职责 |

另有一个此前没讨论到的收益：**NPC 记忆一致性**。现在记忆里可能出现玩家从未参与的事，因为没有任何地方记录"玩家当时在不在场"。

---

## 5. 与 stage-projection 的优先级

**存档事实 > 原著快照。** 具体规则：

1. 相识账本**有**该角色记录 → 关系身份以账本 + 存档关系标签为准；
2. 相识账本**无**记录 → 关系身份一律回落"陌生"，**stage-projection 的关系类字段不得生效**（`role` 里的后宫/侍婢/情人等）；
3. 非关系类字段（外貌、性格、宗派、族裔）**仍以 stage-projection 为准**——那些不依赖玩家轨迹。

第 3 条是刻意的：不能因为这个问题把整个投影机制推翻，它在非关系字段上是对的。

> ⚠️ 这条规则会修正 `cb8c4c7` 的已知局限：该提交按本关 `role` 判断"是否已归属"，而 `role` 来自原著快照。届时判据改为账本优先。

---

## 6. 迁移路径

1. **建账本 + 写入点**：事件激活/完成、同场交谈、传闻送达三处写记录。旧档首次载入时从 `completedEventIds` 回填一次（近似，但比没有强）。
2. **跨关继承**：账本随存档走，不随 stage 重置——这是与现有 `introducedCharacterIds` 最大的区别。
3. **接四个消费者**：优先接在场与 cap（两处已落地，改判据即可）。
4. **降级 stage-projection**：按 §5 规则实施。
