# 1012FIXLIST 第3条：中止与慢回合原因及方案（仅方案，未实施）

依据更正版真机报告与只读复核：99次Chat开始，90次HTTP200、1次503、8次中止；48个UI回合中7个≥30秒，nearest-rank P95 53.051秒。所有尝试保留，不把UI ready当作后台请求完成。

## 原因与证据边界

- 已确认客户端首包截止默认30秒：`src/services/aiRequestDeadline.ts:24`。请求开始后30.003–30.155秒中止与该计时器高度吻合；尚未捕获逐请求异常phase与generationId，不能仅凭ERR_ABORTED把八次都判为服务端慢或用户取消。
- OpenAI流式入口由`src/services/aiService.ts`的`streamingRequestOpenAI`套用deadline。`content_idle`模式取消总时长限制、正文空闲上限为30秒，首包默认仍为30秒。应区分HTTP响应头、SSE心跳、推理字段和首个有效正文，不能把任何网络字节视作可用演出。
- `src/services/modularTurnBackground.ts:94`之后的memory请求使用独立AbortController并异步运行；所以回合完成后仍有请求是现行设计。日志未登记模块/所属回合，F07-87 #14及D1 #18/#22的角色尚未逐一确定。
- HTTP503空输出是一次上游失败，不能计有效完成。53秒/85秒回合可能包含串行intent/narrative/reconcile及重试；仅已有日志无法把全部尾延迟归因一个模块。

## 建议实施次序（待用户裁定）

1. 先补诊断：每个请求记模块、turn/generationId、前台/后台、首次响应头/有效正文时点、结束status/timeout phase、取消发起者；不记密钥或完整提示词。回合日志分别记前台ready与后台drained。
2. 把首个有效内容、正文idle、总截止分开配置到现有API模块设置；不要统一放大30秒。先按模块真实分布制定预算，前台给可恢复超时提示；后台只写失败状态并保留回合/版本守卫。
3. 503/429等可重试失败：限定单次退避重试、同一请求预算、未产生正文才重试；已落账动作/状态绝不重新结算。若已有上层重试则复用，不叠加重试层。明确输入需用户重发的情况。
4. 保持异步memory；离开角色/槽或旧版本任务过期时取消或拒绝落账。不要在每次回合ready时强制杀掉正常后台请求。
5. 固定原失败链与边界组验收：分母含503/abort/所有重试，分别报告首正文、前台回合、后台耗时及P95；验用户取消、迟到、部分正文、503/429、保存切换，保证无重复结算。

本条只调查/方案，未改deadline、重试、模型策略或8097。增加预算只能降低截断，不能等同达成30秒SLA。
