## 0. 结论速览

- **新增存档字段：0 个。** 在队情况和期限状态都从编年史推导出来。期限到了终态才锁存一次，写进 flags 键 `deadline.<id>.state`，做法和 `line.*` 一样。道具来路直接复用现成的 `inventoryTransferReceipts`，这本账已经跨关继承（`strictInitializer.ts:388/467`）。
- **B 道具去重**：剧本里所有发物品的路径都会经过 `settleScenarioInventoryTransfers`（`inventoryTransactions.ts:107`，不在冻结范围）。在这里加一道“唯一道具组”检查：同组物品只要曾经得到过，就跳过这次发放。分组名单由内容组填，首版为空，所以现有行为一个字都不变。
- **E/G 在队**：`party.<characterId>` 以“显式在队账”为准，由三部分组成：规则表里的入队/离队事件、开局在队名单、`departedCast` 记录的死亡或永久离场。两个启发式函数只用于演出，不当合同条件。
- **H 进度期限**：规则表定义期限的起点事件、解除事件和计数刻度，`due/urgentAt` 两个数值放进 numbers 配置。读取状态用 `deadline.<id>`，共五个值：未开始（undefined）／running／urgent／due／cleared。到期后带来什么后果只留接口，例如冰蛊坏结局要不要接，待你拍板。
- **C 身份注入**：新文件生成一行“主角身份”结论，`storyContext.ts` 只需加 1 个 import、1 次调用、1 个模板槽。行内措辞要你拍板，拍板后在同一个 commit 里追加裁定簿条目。
- **冻结文件不用改**：`runtime.ts` 里已有两个挂点。T3 加的 `syncPlayerLedgers` 每回合都会调用；T4 加的 `resolveLedgerPath` 委托会把新路径自动带到激活/完成条件。`AIBidirectionalSystem.ts` 也不用改，因为被跳过的发放不会产生 settlement，模型就没有授权去写这件物品（`AIBidirectionalSystem.ts:2771-2776`）。
- 新增错误码 4 个（`LCQ-SAV-025…028`），调试日志全部挂在现有的 `identity` 大类下，拆成 T5–T9 五个小任务，另有 T10 等拍板后再开。

## 2. B 道具来路去重

### 2.1 字段

- **不加存档字段。** “得过某物”以 `runtime.inventoryTransferReceipts`（已跨关继承）为准：同组里任何一个 itemId 有回执，就算得过。
- 旧档回填时，往同一个数组里补“回填回执”，`transferId = backfill:<itemId>`，`sourceEventId = 'backfill'`，`actionId = 'backfill'`。**不改** `ScenarioInventoryTransferReceipt` 类型；runtime.ts 里按 transferId 判断锦囊回执的逻辑（`:1667`）也不受影响。

### 2.2 规则（`mod-kit/player-ledger-rules.json` 新增可选键 `itemGroups`）

```ts
interface ItemGroupRule {
  id: string;                    // liuchao.itemgroup.<名>，末段不能是 from
  itemIds: string[];             // 同一件东西在各书里的 id；≥1 个
  /** 本组已得过时怎么办：缺省 'skip'（不发）；'redirect'＝改发 redirectItemId（如何改发由内容决定） */
  whenHeld?: 'skip' | 'redirect';
  redirectItemId?: string;
}
```

- 首版为 `[]`。哪些物品是“唯一”、哪些 id 算同一件，由内容组填（Q6）。T5 附带一个只读脚本 `scripts/report-item-group-candidates.mjs`，列出 22 组同名候选给内容组参考，**脚本不会自动写入**。
- “回收”（把已经发出的物品收回来）不支持，见 §11。

### 2.3 写入点

新文件 `src/modules/scenarioMods/itemProvenance.ts`：

```ts
export type ItemGrantVerdict =
  | { action: 'grant' }
  | { action: 'skip'; groupId: string; firstFrom: string }
  | { action: 'redirect'; groupId: string; itemId: string };
/** 纯判断：本组是否已得过（回执，按 dedupeBy 再并上当前背包持有）。规则表为空时恒为 grant。 */
export function itemGrantVerdict(save, runtime, itemId: string): ItemGrantVerdict;
/** 读档回填：本组成员当前在背包里（数量>0）却没有回执的，补回填回执。幂等。 */
export function backfillItemReceipts(save, runtime): number;
```

- `inventoryTransactions.ts:109` 之后、`catalog.get` 之前加一次判断：`skip` 就 `continue`；`redirect` 就改用 `redirectItemId` 继续往下走，回执的 transferId 记为 `${transferId}:redirect`，`itemId` 写改发后的物品。判断函数内部自带 try/catch，出错时返回 `grant`，也就是按原逻辑发放、不拦截，同时记 `LCQ-SAV-025`。
- 同一次调用里给了同组两件物品时，第一件发出后会马上写进 `settledIds` 和回执，第二件按 skip 处理。
- 被跳过的物品**不产生 settlement**，所以 AIBS 授权给模型的物品清单（`grantedIds`）里不会有它，模型也就没法在正文里“补发”。
- `loadRepairs.ts` 的 `applyLoadRepairs` 里加一行 `backfillItemReceipts(save, rt)`，返回值新增字段 `itemReceiptsBackfilled`。

### 3.2 规则（`player-ledger-rules.json` 新增可选键）

## 4. H 按剧情进度计的期限

### 4.1 语义（只做通用机制，不定具体期限）

一个“进度期限”从**起点事件**完成时开始计。之后每完成一个**刻度事件**，计数加一。计数达到 `due` 就到期；在到期之前完成了**解除事件**，就算解除。同一个机制可以表达两种需求：冰蛊这类“期限到了会出事”，以及凝羽归队这类“过了门槛才能做某事”。到期以后怎么样（坏结局、开放接回、只换文案）**不在机制里**，内容用 `deadline.<id> eq due` 自己接。

### 4.2 字段

- **不加存档字段。** running 和 urgent 每次读取时现算。到了终态（`due` 或 `cleared`）就锁存进 flags 扁平键 `deadline.<id>.state`，写一次之后不再改。理由是 `due/urgentAt` 可以通过 tuning.json 热改，如果不锁存，改了数值会让已经到期的存档倒退回 running。
- `deadline.` 的处理照搬 `line.` 的三件套：切关时加进 flags 继承白名单（`strictInitializer.ts:408` 旁边）；`canonGuard.ts:358` 旁边加“只能由引擎写”；`questLines.ts:63` 旁边禁止 `setState` 写这个前缀。

### 4.3 规则（`player-ledger-rules.json` 新增可选键）

```ts
interface ProgressTick { eventId: string; lineId: string }       // 一个“主要段落”＝一个刻度；lineId ∈ 7 条国家线
interface ProgressDeadlineDef {
  id: string;                     // liuchao.deadline.<名>，末段不能是 state
  name: string;                   // 展示名（调试日志、提示词用）
  startEventIds: string[];        // 任一完成即起算；取最早的那个（先到先得）
  clearEventIds: string[];        // 起算后任一完成就算解除；起算前完成的不算
  excludeLineIds?: string[];      // 这些线的刻度不计（如“在其他国线完成 N 段”）
  /** 逼近演出的可观察事实（裁定 #155：不写剩余数，不预告结局）。内容组写，首版不填 */
  promptCue?: { urgent?: string; due?: string };
}
progressTicks?: ProgressTick[];
progressDeadlines?: ProgressDeadlineDef[];
```

计算方法（纯函数，输入是 `orderedDoneEventIds`）：
1. `s`＝起点事件第一次出现的位置。没有就返回 undefined（未开始）。
2. 从 `s` 之后逐个看：遇到解除事件就记 `c`，停止；遇到刻度事件（并且所属线不在 exclude 里），计数加一，计数等于 `due` 时记 `d`，停止。同一个事件既是刻度又是解除时，**先判解除**。
3. 有 `c` → `cleared`；有 `d` → `due`；计数 ≥ `urgentAt` → `urgent`；其余 → `running`。
4. 已经锁存的值优先，计算结果和锁存不一样时以锁存为准，并记 `LCQ-SAV-027 latch_conflict`。

## 6. 原稿 §11 Q4–Q6 推荐答案

- **Q4 `party.*` 以什么为准** → **推荐采用显式在队账**（§3），由三部分组成：规则表里的入队/离队事件（可以用路径回执区分玩家的选择）、开局关在队名单、`departedCast` 的死亡或永久离场。启发式的 `currentTravelCompanions` / `presentCompanionIds` 只用于演出，不做合同条件。不加存档字段，从编年史推导，所以任何先后顺序都能得到确定的结果。
- **Q5 编年史上线前的旧关回填不到** → **推荐接受这个缺口，不按关卡顺序推断回填 `done.*`。** 理由有三。①编年史 07-16 就上线了，缺口只出现在三个多月前的旧档上。②推断会把没亲历过的可选事件也判成 done，进而触发“已完成提及”“换由头”这类错误变体。漏判的后果只是走原著默认（乱序方案总原则“默认就是原著”），比误判安全。③唯一需要补的是道具：漏判会导致**重复发放**，所以只做窄回填，把背包里现有的唯一道具补成回执（§2.3）。读档时如果发现“当前关不是首关、编年史里却没有任何事件条目”，打一条 `identity` 调试日志，方便排查。
- **Q6 规则表由谁供、何时供** → **推荐流程**：剧情策划按乱序方案 §三的检查表，逐线产出一份“账本清单”（markdown 表，放在 narrative-drafts）。列包括：身份定义（id/kind/线/势力/rank/secret）、授予/撤销事件、收束事件与档位、唯一道具组、入队/离队/开局在队、进度刻度事件、期限定义。总策划审一遍，标了【须用户拍】的条目由你拍板。工程只负责把表转成 JSON，跑 `validatePlayerLedgerRules`，有未知 id 就直接报错，**不补写内容**。数值（rank、期限 due/urgentAt）由总策划给，分别进 identities.json 和 numbers-progress。**时机**：某条线的事件 id 进了代码（index 里有 kind=event）之后，才能填那条线的清单。顺序照乱序方案 §五：南荒 → 晋 → 宋 → 汉 → 唐 → 秦 → 太泉。

## 7. 七线任意顺序覆盖

- 四项机制都只认状态：道具看回执，在队、期限、身份都看编年史顺序。没有任何一处写成“先 X 后 Y”。
- 每项都有“七线全排列（7! = 5040 种）”的测试：每条线给一组夹具事件，逐个顺序跑推导，断言不变式成立。断言内容：同组物品只发一次，来路等于最先结算的那次；在队情况只由最后一次相关事件决定；期限状态只取决于解除事件和第 due 个刻度谁在前；身份结论行只取决于账本内容。
- 太泉不判档不影响这几项：太泉事件照样可以当刻度、授予身份、改在队，只是不写 `line.taiquan.outcome`。
