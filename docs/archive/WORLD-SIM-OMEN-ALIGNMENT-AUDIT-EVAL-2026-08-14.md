# 征兆"选题错位"闸门：两种候选方案的实测

日期：2026-08-14
背景：燕歌二审发现 `lyg.changgan_interlude` 六条征兆写成了本关别的事件的情节（P0，已修）。生成期校验与回归测试对这一类缺陷都是盲区——它们只看字段相等、禁用词、拉丁残留和人物 ID 边界，感知不到"整段情节挪错位置"。本文记录为它找闸门的两次实测，结论是**一个否掉、一个可用但需要按下述形态使用**。

## 方案一：确定性专名重合度（否决）

对每条征兆计算其正文与本关**每个**事件文本的中文词重合度，若最贴近的不是自己的 `sourceEvent` 则告警。

在全部 357 条精修（含已关门的清羽／云龙）上实测：

- 告警 22 条，逐条人工回读后**真错位 4 条**（全部落在 `changgan_interlude`），**误报 18 条**。
- 该关实际有 6 条错位，即**召回 4/6**，漏掉 `_06`／`_09`。
- 重合分数普遍是 0 vs 1——征兆是改写而非复述，专名重合本就稀薄。

召回与精度都不够，不采用。

## 方案二：Grok agent 模式只读审计（可用，但要按 C 段形态用）

用本机 Grok Build CLI 的 agent 模式（`--permission-mode plan` 只读、`--cwd` 指向隔离目录），让它自己读 stage JSON，逐条判断每条 baseline 征兆的选题是否对应自己的 `sourceEventId`，输出结构化 verdict。

### A. 带标签的召回测试

用提交 `4e4ff34`（修复前）的 `lyg.changgan_interlude` 作真阳性标签（10 条中 `_04`–`_09` 六条已知错位），另加两关作对照，共 30 条：

| 指标 | 结果 |
|---|---|
| 覆盖 | 30/30 |
| 已知错位召回 | **6/6** |
| 对照组误报 | **0/24** |
| 成本／耗时 | $0.37，8 次模型调用，4m44s |

归属判断与人工结论一致（`_04→_07`、`_05→_06`、`_09→_10`），其中 `_06→_09`、`_07→_09` 两条是方案一完全没抓到的。证据具体到可复核，例如"通篇太医院药单与赵飞燕病势真假，讲的是赵飞燕病线，不是囊瓦拒商会、加码兑付的密约谈崩"。

### B. 干净数据上的误报测试

用修复后的燕歌全部 10 关／106 条（已确认干净，任何 misaligned 都是误报），逐关独立审计：

- 判定 97 条，**misaligned 0 条**，成本 $1.63。
- **但 10 关里有 1 关（`lyg.mijing_rumen`，9 条）返回空结果**，没有任何 verdict。

合并 A、B：在 121 条干净条目上误报 0，在 6 条已知错位上召回 6。

### C. 可靠性观察与由此决定的使用形态

它的**判断质量**好，**交付**不可靠：

- B 段有 1/10 的运行返回空 entries；A 段的正式输出前也先吐了 5 个空的 `{"entries": []}`。
- A 段产物里的 `thought` 轨迹显示中间推理剧烈抖动：中途出现过至少三个互相矛盾的版本，还编造过不存在的 situationId。**最终答案对，不等于过程稳定。**

关键在于：**交付缺口是可机械检测的**（判定条数 ≠ 该关 baseline 条数），而判断质量不可机械检测。所以应当这样用：

1. 作为 merge 之后的**审计步骤**，逐关跑，输出 `align-issues.json`。
2. 对**覆盖**fail-closed：条数对不上就重跑该关——与已有的"placeholder 凑数即拒收"同一套路。
3. 对**结论**不 fail-closed：判 misaligned 的条目送人工回读再定夺，不直接拦批次。

### 未采信为强结论的部分

- 样本量小；6 条真阳性全部来自同一次退化，不能代表所有错位形态。
- 判官与生成方是同一模型家族，存在自审偏置的理论风险（本次未观察到，但样本不足以排除）。
- 本文只做了实测，**尚未实现为管线命令**——落地是后续工作。

## 现状

方案一已否决。方案二按 C 段形态可用，但尚未接入管线；在接入前，同类精修批次的"选题错位"仍依赖人工对齐抽检 + 独立二审。
