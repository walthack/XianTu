# 游戏四角色协作框架

建立日期：2026-10-01（SGT）。适用项目：XianTu／六朝。
成熟度：框架初稿；未配置应用、未派发制作任务、未启动自动调度。

## 1. 目标与权威

用主策划、模块策划、剧情策划、游戏测试形成「体验目标 → 设计合同 → 实现 → 独立测试 → 返修 → 收口」闭环。角色是职责，模型是执行工具；角色不因换模型而改变。

- 用户负责产品取舍、正典人工裁定和授权边界。
- Grok 保持唯一执行控制面：登记批次、分配任务、处理依赖、汇总门禁并确认收口。主策划由控制面承担。
- `PROJECT-STATUS.md` 是项目状态权威；`docs/PLANNING-ROUNDS.md` 记录同批次各组交付与方向复核；不另建一份竞争性的总状态。
- 正典人工裁定以 `mod-kit/generated/deepseek-v4-flash/character-canon/CANON-DECISIONS.md` 为准。
- 独立只读二审走既有 Claude 包装器；满足项目切换条件才用 Codex CLI。Codex提供方向与证据复核意见，正式收口仍由控制面确认。
- 文档旧分工若与现行 AGENTS.md 的控制面／审核路由冲突，以现行指令为准；本框架不把历史已授权的 Claude 模块实现改判为违规。

## 2. 四角色

| 角色 | 核心责任 | 必交成果 | 可决定 | 必须上交的问题 |
|---|---|---|---|---|
| 主策划 | 体验方向、优先级、范围、排期、任务拆分、跨组裁定与收口 | 轮次目标、任务单、依赖与写入分工、阶段结论 | 授权范围内排序、分工、返修去向 | 新产品取舍、正典解锁、授权外的成本／发布／数据改动 |
| 模块策划 | 把玩法设计成可实现规则；授权后实现、聚焦测试和自查 | 模块合同、接口、失败恢复、候选补丁、门禁与交接包 | 合同内技术细节；提出规则替代方案 | 影响玩家选择／代价的规则变更、正典冲突、跨模块写权限 |
| 剧情策划 | 角色动机、知情、事件顺序、选择文案、演出边界与后果 | 事件合同、来源依据、文案、正反例与跨拍承接 | 已批准合同内的表现方式 | 正典变更、新分支结果、玩法结算变化、保护字段 |
| 游戏测试 | 独立检查可玩性、规则、剧情与性能；提交可复现缺陷 | 测试书、候选基线、逐项结果、原始日志／截图、缺陷单、复测报告 | 证据支持范围内的测试结论、阻断建议 | 设计预期冲突、无法复现、环境／授权阻塞 |

模块策划设计并维护规则与状态写入；剧情策划设计并维护人物与演出材料；双方共同确认事件合同。游戏测试不替代策划裁定，不能用「我觉得应当成功」重写结果。实现者的自测不能充当自己改动的独立验收。

## 3. 一轮的完整流程

1. 主策划读最新状态、最新轮次和当前反馈，为一个可验收的玩家体验登记同一批次编号；冻结目标、范围和成功标准。
2. 模块与剧情各自认领小节，先对齐事件合同。允许独立准备材料；共同接口未确定时，不实现会写入冲突状态的部分。
3. 控制面确认设计合同与写入分工。产品／正典未决问题先做可审阅方案交用户；其他部分继续。
4. 实现负责人完成窄范围补丁及自查，交付「候选基线＋差异＋测试证据＋未测项」。剧情同步核对玩家可见文案。
5. 按既有路由完成独立审核；失败不是 PASS，失败原因与 findings 留档。审核和浏览器测试须注明具体候选版本。
6. 独立游戏测试先测阻断检查点，再测连续旅程、保存恢复和真实模型表现。环境或模型不可用时，保留 BLOCKED／NOT_PROVEN。
7. 缺陷回到主策划：规则／生命周期交模块，动机／知情／演出交剧情，接口冲突双方共同处理。控制面指定一名返修 owner。
8. 修改后对新候选做聚焦复测；影响扩大才扩回归。主策划核对验收标准和剩余缺陷，记录收口或继续返修的依据。

同轮交付状态可用：计划中 → 设计中 → 待实现 → 实现中 → 待独立审核 → 待真机 → 返修中／待收口 → 已收口。阶段状态只是证据摘要，不是跳过审核或测试的许可。

## 4. 共享交接合同

每项任务使用以下格式，写进轮次小节或链接的任务文档。口头消息用于提醒，文件用于交接。

```markdown
任务ID／执行批次：
负责人／接收角色：
工作目录：
玩家体验目标：
依据：用户原话／反馈ID／设计与正典链接
范围：涉及模块、事件ID和文件
权限：可改内容；不得触碰的正式配置／存档／保护字段
候选基线：HEAD＋dirty差异清单／快照标识；运行测试另记bundle
输入与依赖：
验收场景与明确预期：
交付文件与状态：
证据层级、日志链接与未测项：
剩余问题／下一接收人／建议下一动作：
```

候选 HEAD 相同但 dirty 不同，仍属于不同候选。交接包须记录测试时的差异快照或摘要；后续代码变化必须标记结果是否仍适用。

事件合同至少含：困局、人物欲望、玩家已知事实、合法行动、可知代价、判定、状态写入、正文可说的结果、拒绝／失败后局面、延迟后果、下一拍、验收正反例。正文不能代替引擎结算，规则也不能越过角色意愿。

模块合同至少含：输入快照、输出、消费者、写权限、串并行依赖、预算、取消／迟到／重试规则、幂等性、存读档兼容和玩家可见失败反馈。

## 5. 证据与缺陷

| 证据层级 | 能证明 | 不能据此宣称 |
|---|---|---|
| 静态／源码复核 | 合同、路径、来源及显式逻辑 | 实际UI可玩或模型遵守 |
| 确定性测试 | 覆盖输入下的规则与生命周期 | 真实模型质量和延迟 |
| 受控浏览器 | 注入响应下的UI、事务与存储集成 | 真实模型连续旅程通过 |
| 真实模型局部试玩 | 具体场景与配置下的样本表现 | 全路线、所有模型、整体SLA |
| 真实模型连续验收 | 被记录路线、配置、版本及样本的体验 | 未覆盖路线或配置的保证 |

用 PASS／FAIL／PARTIAL／BLOCKED／NOT_PROVEN 表示逐项结论。`READY_FOR_TRUE_DEVICE` 只表示可交真机。30秒目标从玩家提交计到可继续操作，所有超时、中断和失败进入分母，同时报告成功率、中位数、P95、最大值与样本量。

缺陷单包括：ID、严重度、候选基线、环境／模型／路由、检查点、原始输入、操作步骤、预期依据、实际输出与状态、证据、复现次数、影响、建议归属、修复候选与复测结果。脱敏记录，不写API密钥。计时汇总必须能由明细重算。

测试职责还包括：玩家能否理解下一步；选择是否被承认；是否有文本成功但进度没动；角色是否提前知情；失败能否恢复；切档／取消／迟到是否污染；真实模型连续体验及速度。

## 6. 写入与运行纪律

- 开工先读 `git status` 和目标段落。保留现有 dirty；不能 reset、clean 或覆盖其他负责人的改动。
- 同文件同段只有一个写入 owner。共同文档各写自己的小节；主策划汇总公共部分，写前重读。
- 模块与剧情可先分别产出合同；重叠源码修改须串行或使用经确认的隔离工作区。共享服务重启、构建、存储也要协调。
- 真实测试使用隔离 profile／存档，注明端口、运行bundle、模型配置与来源；不以 localhost 受控截图冒充别的设备实测。
- 修改 canon 或核心 prompt 前读裁定簿。保护字段先追加人工解锁裁定再改；未经授权不改正式save/API。
- 代码检查按项目门禁执行：聚焦验证、type-check、完整 canon:build、build:single、diffcheck。文档稿不需要运行代码门禁。提交还须符合用户授权与项目提交纪律。
- App中的消息或角色说明不会自动建立调度器。每次由控制面显式派单、检查交付；要自动唤醒、监听和回报需单独配置并验证。
